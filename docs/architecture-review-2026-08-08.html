二、整体架构合理性分析

2.1 应保留的设计基因（不许任何重构破坏）

  • 协议先行 + fail-closed：所有跨进程消息在 packages/protocol 用 Zod 严格校验，显式 schemaVersion，未知字段/版本默认拒绝；链路断开时返回 503 并清空镜像，绝不沿用旧状态或伪造成功。
  • 控制平面分层清晰：Browser → Dashboard → Control API → Coordinator → Runtime 五层职责单一，权限逐层收窄；浏览器拿不到长期令牌，坐标读取需单独权限，停止命令需二次确认 + 本地确认码 + Runtime 真实回执。
  • 确定性优先的 AI 边界：L0 安全层和技能执行器不接受模型文本；未来模型只能输出白名单技能调用 JSON，且经 Schema、Policy、参数边界三重验证。这为 P2 智能层预留了安全接口。
  • 诚实的验收文化：文档明确区分"已测试/兼容未测试/不支持"、"离线验收/实机验收"，不冒充完成。

四、Rust vs TypeScript 决策

4.1 结论：当前阶段全部保持 TypeScript

这个系统 95% 是 I/O 密集的控制平面（WebSocket 转发、JSON 校验、数据库读写）。Rust 在这些场景的收益接近零，而成本很实际：

  • Bot Runtime 被 Mineflayer 锁死在 Node。27 个 Minecraft 版本的协议适配全靠它；Rust 对应物 azalea 在成熟度、版本覆盖、插件生态上差距很大，迁移等于重写并作废所有已通过的联机验收。
  • 每秒几十条心跳/状态消息的吞吐对 Node 毫无压力，当前没有任何一个已测量的性能瓶颈。
  • Zod Schema 是全链路的单一事实源，TS 类型自动推导；引入第二语言即产生协议双重维护。
  • 对 AI 接管而言，单语言栈的修改出错率远低于混合栈。

4.2 预留的两个 Rust 位置（含触发条件）

模块触发条件（必须先测量）接口边界理由
Rust寻路/世界几何服务多 Bot 后寻路计算开始阻塞 Runtime 事件循环（事件循环延迟 > 50ms 可测量）独立进程，结构化 JSON/gRPC，作为一个"能力适配器"接入A*/体素几何是纯 CPU 计算，是 Rust 的甜点区；不碰 Mineflayer
Rust接入网关Bot 数量 50+ 且 Coordinator 单进程成为已测量瓶颈无状态 WS 终结/转发，协议已版本化可独立替换高并发连接管理，无业务规则
原则：Rust 只放在有清晰 JSON 协议边界、纯计算或纯转发、可独立验收的叶子位置，绝不进入含业务规则的控制平面。在有性能测量数据之前写 Rust 是徒增复杂度。

五、第一版 MVP 设计

5.1 MVP 定义

一个 Bot 在隔离测试服自主完成一件真实有用的事，全程可观测、可停止、崩溃可恢复。
现有代码已完成约 70%——MVP 是补全闭环，不是新起炉灶。

5.2 范围内工作（按依赖顺序）

#工作项说明验收标准
1P1.3.2 持久任务闭环事务 outbox + reconciler（已有 WIP 提交 40b406e）、独立 Worker 应用、跨 Worker 取消、自动过期租约恢复杀掉任意进程后任务不丢、不重、可恢复
2Coordinator 任务调度接入Coordinator 从 PG 领取任务 → TaskDispatchV1 → Worker → SkillInvocationV1 → Runtime。这是目前完全缺失的一环Dashboard 创建的任务能驱动 Bot 真实动作
3审计与注册表快照落 PG复用 task-system 连接层，append-only 审计表Coordinator 重启后审计不丢
42~3 个生产技能gather.wood / craft.item 级别，走既有技能框架与能力适配器每个技能独立离线 + 实机场景测试
5L0 实机危险场景矩阵在真实隔离服构造溺水/岩浆/坠落/饥饿场景L0 真实动作全部正确触发——自主执行任务前的安全前提
6Dashboard 任务看板创建任务、看状态流转、取消任务浏览器 E2E 覆盖

5.3 明确砍掉的范围

多 Bot 协调、AI/模型接入、Docker/便携/网吧模式、正式服务器、Rust、长期记忆、跨主机 TLS。

5.4 MVP 端到端验收场景

Dashboard 创建"采集 16 个原木"任务
   → Coordinator 从 PG 领取并派发（outbox 保证原子）
   → Worker 领取 → SkillInvocationV1 → Bot 在隔离服真实执行
   → 期间人为制造一次溺水，L0 正确救回并恢复任务
   → 中途杀掉 Worker 进程，租约过期后任务被自动回收重派
   → 完成后 Dashboard 显示结果与产物数量
   → 全程同一 traceId 贯穿五个进程的结构化日志，审计可查
